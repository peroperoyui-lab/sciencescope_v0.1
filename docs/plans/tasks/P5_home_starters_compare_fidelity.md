## 目标

1. 首页「从这里开始」的四张卡片和项目进度由秘书按最近离开的那个项目来写，所有项目共用一份，最新的覆盖旧的。
2. 带批注的段落改了字、改了格式，比较时照常显示逐字差异和格式差异，不再拆成整段删除加整段新增；同一位置有多个原子时不再多出假的删增。
3. 分支改名的后端只保存合规的名字。
4. 划选改写不再往正文里加原文、指令和读到的材料里都没有的判断。
5. 弄清 Windows 上首屏那 2.2 秒样式计算和字体有没有关系，给出有数字的意见。

## 用户会怎么用

- 用户在「城市韧性研究」里聊了一阵，切到别的项目或回到首页。过一会儿首页顶上写着这个项目进行到哪一步，下面四张卡片是秘书按这个项目现在的状态写的下一步，点一下填进输入框，不会自己发出去。之后用户离开另一个项目，首页就换成那个项目的进度和卡片。
- 秘书写不出来时（没有模型、关了「离开项目时整理」、请求失败或返回的格式不对），首页保留上一份；一份都没有时，界面照旧用模板卡片。
- 用户在工作站比较 v3 和 v5。v5 在一段里删了两个字、加粗了一个词，还加了一条批注。比较页上这段左右对齐，删掉的字标红，加粗的词有格式标记，不会把整段标成删除再整段新增。

## 要做的

每部分都写修前、修后的现象或数字。

1. **首页卡片由秘书写**（新后端）：
   - **什么时候写**：
     - 用户离开一个项目时写，也就是 `POST /api/projects/:id/focus` 收到 `{ focused: false }`；切到别的项目、回到没有项目的首页都算离开。
     - 等这个项目因为离开而触发的纪要刷新（`minutes.js` 的 `focus` 用 `'leave'` 调 `projectMeetings`）跑完再写，这样读到的是新纪要。
     - 退出应用时正在打开的项目，下次启动后补写一次。可以复用 `secretary_pending_projects` 那套机制，也可以单独记，在报告里说明选了哪种。
     - 开关沿用设置里的 `summary.onLeaveProject`（秘书页「离开项目时整理」），不新增设置项。关掉就不写。
   - **省 token**：
     - 每个项目留一份上次写的结果，并记下当时输入的指纹：用到的纪要修订、计划修订、最新版本 id、专家名单。
     - 离开时如果指纹没变，就把那份结果重新设为首页当前的一份，不调模型。
   - **写什么**：一次秘书请求，复用 `services/secretary/background.js` 的 runner 和秘书模型（runner 要对话 id 时用这个项目最近活动的那段对话），返回 JSON：
     - `progress`：一到两句、不超过 80 字，说这个项目现在进行到哪一步。
     - `cards`：恰好 4 张。每张是：
       - `icon`：只能从这几个里选：`lightbulb`、`circle-help`、`scale`、`list-checks`、`database`、`file-pen`、`search`、`book-open`。
       - `title`：不超过 24 字。
       - `sub`：不超过 30 字。
       - `text`：放进输入框的话，不超过 200 字，不带 @。
       - `expertId`：卡片要找的专家的 id；不找专家时为 `null`，后端核对它在当前专家名单里。
     - 界面会用专家当前的名字在 `text` 前补上 `@名字`，所以专家改名后卡片不过时。
   - **输入**：
     - 项目名。
     - 最近活动的至多 3 段对话的最新纪要。
     - 计划里未完成的条目。
     - 最近的文稿（名字、第几版）。
     - 专家名单（id、名字、一句话角色）。
     - 现有模板卡片的写法作为例子：`app/ui/home-next.js` 的 `starters`，可以把这几条例子挪到 `app/shared/` 两边共用。
     - 指令里写明：进度和卡片只能根据这些输入，不编造没有的进展、数据或结论。
   - **校验**：
     - 返回不是有效 JSON、不是 4 张、图标不在清单里、字段超长、`expertId` 不存在时，都不写入，保留上一份，记一条后台失败。不要截断凑数。
     - 用量照现有秘书后台请求的方式记录（runner 记下 turn 和 usage），报告写一次写卡片的 token。
   - **读接口**：`GET /api/home/starters`。
     - 返回 `{ slot: { projectId, projectName, progress, cards, writtenAt } | null }`。
     - 项目已删除或已归档时返回 `slot: null`。
     - 专家已删除的卡片把 `expertId` 改成 `null` 再返回。
   - **事件**：写入或重新设为当前时发一个事件（例如 `home.starters.updated`），界面据此重读。
   - **存储**：全局一份，加上按项目留的上次结果。放数据库新表（加迁移）或 workspace 资源都可以，在报告里说明理由。不进知识库。
   - **测试**：
     - 离开触发写入。
     - 两个项目先后离开，后者覆盖前者。
     - 指纹没变时不调模型。
     - 关掉 `onLeaveProject` 不写。
     - 无效 JSON、3 张卡、未知图标、未知专家时保留上一份。
     - 项目删除后读到 `null`。
     - 专家删除后对应的 `expertId` 变成 `null`。
     - 下次启动补写。
     - 用测试运行时模拟模型，不调真实服务。

2. **带批注段落的配对**（P4c 第 7 节 v3→v5）：
   - 现状：
     - `app/services/desk/diff-blocks.js` 的 `describeBlock` 把每个原子写成 `<类型:XML 的 sha256>` 拼进配对文本 `key`。
     - 批注的 comment-start、comment-end、comment-reference 每个都带一段 64 位哈希，加一条批注就让相似度掉到 0.17，低于 0.4 的阈值，于是段落被拆成整段删除和整段新增，`comparePair` 和格式比较都没有运行。
   - 改为：
     - 批注定位用的原子不进配对文本，也不算正文的删增。批注本身的新增和修改不在比较页显示（批注在「批注与索引」里看），这次不做。
     - 其他原子（图片、公式等）在配对文本里换成短的、稳定的占位，让原子的身份不再按哈希长度影响相似度。原子内容变了仍然算一处改动。
     - 行为照旧：无批注段落的比较结果不变，图片换了照常标出。
   - 测试：
     - 同一段同时删字、加粗、加批注时，配对成功，删 2、增 0、格式 1（用报告里的合成文稿重做一份，不提交私人材料）。
     - 只加批注时，比较结果是零处改动。
     - 换图片时标一处改动。
     - 原有的 `diff.test.js` 全过。

3. **同位置多原子**（P4c 第 7 节 v5→v6）：
   - 现状：`app/services/desk/diff.js:89` 在未改动区域里用 `find` 按 from/to 取第一个原子；comment-end 和 comment-reference 同在 `[19,19)` 时互相认错，多出零长度的删增并计入总数。
   - 改为：同一位置的原子按顺序和身份一一对应，零长度原子不再产生删增。第 2 部分让批注原子不算删增之后，这里对其他同位置原子（例如紧挨着的两张图）仍要对。
   - 测试：
     - 同一位置两个不同原子不变时，零处改动。
     - 同一位置两个原子换了顺序时，按实际改动标出。
     - 只加粗另一段时，只有格式 1。

4. **分支名校验**（后端已有改名）：
   - 现状：
     - `PATCH /api/versions/:id` 传 `branch` 时，`services/versions/graph.js` 的 `updateMetadata` 会把整条分支改名，重名时返回 `BRANCH_EXISTS`。
     - 但它不去首尾空白，接受空字符串（会变成「主线」），也不限长度。
   - 改为：
     - 去首尾空白。
     - 空名字返回清楚的错误码。
     - 不超过 40 个字。
     - 和原名相同时不算改动，也不发事件。
     - 事件里带上旧名和新名，方便界面提示。
   - 界面上的改名入口由 Claude 做。
   - 测试：去空白、空名、超长、同名、和别的分支重名、改名后同分支所有版本都换了名字。

5. **改写不加无依据的内容**（P4c 场景 2）：
   - 现状：划选改写（`app/services/desk/rewrite.js` 发到绑定对话，由专家用文稿工具改）保留了数字和限定，却自己加了「方向上与预期一致」。指令、原文和这轮读到的 12 个块都没有「预期」。
   - 改为：
     - 先找到改写这条链上模型看到的说明，在报告里列出来：发给对话的那条消息、`manuscript-tools.js` 里改写工具的描述、专家默认说明里有关的段落。
     - 在最贴近改写的那一处加一条规则：改写只用原文、用户的指令和这一轮读到的材料里有的内容，不新增事实、判断、预期或结论；觉得需要补的，在回答里提出来，不写进正文。
     - 不改模型，不加二次审查请求。
   - 测试：
     - 一个检查说明里有这条规则的单元测试。
     - 用 OpenCode Go 的 `deepseek-v4.1-flash`，在全新测试安装上把场景 2 用同一份自造材料跑 3 次。每次逐句对照，写出有没有无依据的补充，以及请求数和 token。
     - 3 次里仍有，就如实报告，不反复重跑去挑结果。

6. **Windows 首屏字体对照测量**（只量，不改产品）：
   - 现状：
     - P4c 的 trace 里，首屏单次 `UpdateLayoutTree` 约 2.1–2.2 秒，云端 Linux 上同一界面只有 6 毫秒以内。
     - `app/ui/styles/tokens.css` 的字体栈依次是 `'Noto Sans SC Variable'`（随包，`/vendor/fonts/noto-sans-sc/index.css`，有大量 unicode-range 分片），然后是 `'Noto Sans SC'`、`'Microsoft YaHei'`、`'SimHei'`、`'PingFang SC'`、`'Noto Sans CJK SC'`。
     - 衬线栈是 `'Noto Serif SC'`、`'Source Han Serif SC'`、`'Songti SC'`、`'SimSun'`。
     - 怀疑 Windows 上没装的字体逐个回退，或分片太多，拖慢了样式计算。
   - 做法：
     - 在同一台机器、同一个测试安装上，每种配置冷启动、热启动各 5 次，记录 `UpdateLayoutTree`、首屏时间、字体请求数，取中位数。
     - 换配置只用临时注入的样式或改安装目录里的副本，不提交。
     - 对照四种：
       - A：现状。
       - B：去掉随包 Noto 的样式表，正文用 `'Microsoft YaHei'`。
       - C：保留随包 Noto，只把没装的字体从栈里去掉。
       - D：衬线栈也只留本机有的。
     - 报告里写出本机实际装了哪些字体。
   - 意见：哪种配置值得改、预计收益、观感上的差别（每种附 100% 和 125% 首页截图）。字体换不换由 Yui 和 Claude 定。
   - `tools/perf/` 里可以加一个复测脚本。
