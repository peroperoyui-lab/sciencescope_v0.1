## 目标

1. 用户把一个大文件夹设为项目文件夹后，很快就能在知识库和项目资料里按文件名找到每个文件，解析在后台慢慢做完。
2. 后台解析不卡界面、不挡对话，能看到进度，关掉应用再开会接着做。
3. 先把 KB-7 的带向量评测重跑一次，决定检索扩展默认开不开。

## 用户会怎么用

- 用户的项目文件夹有两万个文件（论文、数据、代码、图片）。设为项目文件夹后一两分钟内，项目资料里所有文件都在，状态是「排队解析」；搜文件名能找到。
- 之后后台逐个解析，项目资料顶部写"正在解析 3,120 / 20,000"（界面由 Claude 做，这次只给数据和事件）。这时照常对话、检索，不卡。
- 解析到一半关掉应用，再开时从没解析完的继续，不重复复制、不重复解析已完成的。

## 要做的

0. **KB-7 带向量重评（先做，单独提交）**：main 上 `node app/services/knowledge/retrieval-eval.js <.sciencescope-local/temp/kb-7b> <本机 multilingual-e5-small 目录>`，报三组的一般题、方法题前 3 命中率和前 12 覆盖率。按 KB-7 的规则：一般题不变差、方法题前 3 有提升，就把 `knowledge.retrievalExpansion` 默认改成 `true`（设置默认值、§5 第 6 条、FEATURES 同步改）；否则保持关，报告里列出方法题每题前 3 是什么。
1. **两段式扫描**：
   - 第一段（快）：列出文件 → 和已有记录比路径、大小、修改时间 → 新文件和变了的文件建或更新资料记录，状态 `queued`，写文件名那条 FTS 记录（按文件名能搜到）。分批事务写库（比如每 500 个一批），不在这一段算哈希、复制、解析。移动检测：路径消失的记录先留着，到第二段算出哈希后再配对。
   - 第二段（后台）：按队列逐个算哈希 → 复制副本（按哈希去重）→ 解析或「仅索引文件名」。哈希和已有记录相同就只改路径（移动），不重新解析。并发 2（可调常量），每个文件一次读盘尽量同时算哈希和复制。
   - 删除：第二段做完、确认没有被配对成移动的，才删除消失的记录（和现在一样，读失败时不删）。
2. **队列持久化**：队列就是 `contentStatus='queued'` 的记录，重启后按项目继续；不新建表就能做到最好。正在解析时用户删掉了文件、关掉项目或改了项目文件夹，跳过并按现有规则处理。
3. **进度和事件**：现在 `POST /api/projects/:id/index` 等整次扫描做完才返回，改为第一段做完就返回原来的计数（`added`、`updated` 等，另加 `queued`），不等后台；新增 `GET /api/projects/:id/index` 返回 `{ phase:'listing'|'indexing'|'idle', total, done, queued, failed }`；用 `index.scan` 等结果的调用方（测试、工具）另给一个等后台做完的方法；进度变化节流后发 `research.index.progress { projectId, ... }`（每秒最多一次），结束发现有的完成事件。`app/ui/api.js` 的 `EVENT_TYPES` 只加这一项。
4. **不挡别的事**：后台解析在主进程时，每个文件之间让出事件循环；大 PDF 解析本来在哪里跑就在哪里跑，不改解析器。检索和对话在后台解析期间照常响应（测试里量一下检索延迟）。
5. **测试**：合成目录（测试里生成 2,000 个小文件即可）：第一段结束时全部能按文件名搜到、状态 `queued`，没有复制和解析；第二段完成后状态正确、副本按哈希去重；中途关闭再开继续，不重复解析；移动（同内容换路径）不重新解析；删除只在第二段确认后执行；读失败不删除；进度事件节流；`listing` 期间再次请求扫描会合并。
