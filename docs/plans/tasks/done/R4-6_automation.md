## 目标

用户给主专家一个目标，主专家连续工作多轮，直到完成、需要用户处理、被暂停或结束。它可以查资料、跑 Python、改计划和日志，每轮的输出照常出现在会议里。

用户离开这场会议时，侧栏能看到哪些会议在后台运行、排队或已暂停。

行为以旧版为准：
- 规格：`docs/archive/legacy/SYSTEM_SPEC_2026-10-18.md` §2.3 的"自动化"部分（审批部分不做）；
- 旧代码：`desktop/execution.mjs`（菜单、目标面板）、`desktop/background-activity.mjs`（侧栏后台状态）、`scripts/execution-service.mjs`。

旧版靠 DSH 自带的 goal 服务实现。新核心按 `docs/architecture/CORE_MODEL.md` §6 的 `autonomous` 发言规则写在调度器里，不依赖运行时的 goal 功能（原则 7：运行时可替换）。

## 6a 自动化发言规则

- **发言规则**：`meetings.policy_json` 设为 `{ mode: 'autonomous', respondent, goal }`。
  - 只用于普通的主会议；秘书会话、助手会议不提供。
  - 和"有序讨论"互斥。
- **目标状态**：用新迁移（014 起）建表保存，不放消息 `refs`。字段：
  - 目标文本；
  - 状态：执行中 / 已暂停 / 需要处理 / 已完成 / 已结束 / 失败；
  - 已开始轮数、最多轮数；
  - 结束原因；
  - 开始和更新时间。
- **循环**（写在 `conductor.js`，每轮仍走现有的 `turn-runner.js`，不改它的结构）：
  - 设定目标后开始第一轮；
  - 每轮正常结束后，如果目标仍是"执行中"，排下一轮。
  - 下一轮的输入由上下文组装模块生成：目标、已进行的轮数、"继续朝目标工作；完成或无法继续时调用 `goal_update`"，以及这期间用户新发的消息。
- **工具** `goal_update { status: 'complete' | 'blocked', summary }`：
  - 所有角色共用（原则 2），只对当前会议的目标起作用；
  - `complete` → 已完成；
  - `blocked` → 需要处理：等用户回复，用户回复后自动继续。
- **停止条件**：
  - 模型调用 `goal_update`；
  - 用户暂停或结束；
  - 达到最多轮数；
  - 一轮失败。失败时转为"已暂停"，保留错误原因，用户可以继续。
  - 最多轮数是用户为每个目标设的值，默认 30，可以在目标面板里改；它是用户自己的用量设置，不是硬上限（原则 4）。
  - 旧版固定 256 轮，这次改为可设。
- **用户在执行中发消息**：进入现有的排队（R4-11），在下一轮的输入里带上，不打断当前这一轮。
- **暂停 / 继续 / 结束**：
  - 暂停：当前这一轮跑完后不再排下一轮；
  - 结束：中断当前这一轮，目标转为"已结束"；
  - 继续：从下一轮接着做。
- **重启**：程序重启后，执行中的目标转为"已暂停"，不会自动继续（旧版行为）。
- **纪要**：自动化的每轮照常触发秘书的总结规则（R4-4）。
- **事件**：目标状态变化发 `goal.changed`，界面据此刷新，不轮询。

## 6b 目标面板与后台活动（按旧结构复刻）

- **输入框的执行菜单**，位置沿用旧版"询问 / 完全接管 / 自动化"菜单（`data-v="mode-menu"` 这一类）：
  - 只有两项："常规"（每条消息回答一次，默认）和"自动化"；
  - 说明文字放进 i 提示。
  - 有序讨论模式下，"自动化"不可选，并说明原因。
- **设定目标**：
  - 选"自动化"后，输入框发送的这条消息成为目标；
  - 发送前可以改"最多 N 轮"。
- **目标面板**（消息列表上方，旧版 `#execution-state`）：
  - 显示：状态、已进行 / 最多轮数、目标文本（可展开）；
  - 按钮：暂停 / 继续、结束目标；
  - 需要处理时，显示模型给的原因；
  - 已完成时，显示模型的总结。
  - 不显示 token 等内部数据（原则 6）。
- **侧栏后台活动**：
  - 每场会议在项目与聊天树里显示状态角标：运行中 / 排队中 / 已暂停 / 需要处理 / 已完成 / 失败。已完成和失败的角标在用户打开该会议后消失。
  - 有会议在后台运行时，侧栏顶部显示"后台任务 N · 查看状态"，点开列出这些会议，点击跳转。
  - 普通回答（非自动化）在后台进行时也显示"运行中"。
- 浏览器和原生窗口行为一致；全局助手面板里不显示目标面板。

## 不做的

- "询问 / 完全接管"、审批卡片、受保护路径审批（原则 5）。
- 关掉程序后继续在后台执行（旧版也不做）。
- 专家在自动化里自动发起讨论；秘书或助手的自动化。
- 不改 `turn-runner.js` 的结构，不改旧线和旧样式表，不加安全测试。

## 完成标准

- **6a 服务测试**（脚本化运行时，每条用户路径一个）：
  - 设定目标后连续多轮，模型调用 `goal_update complete` 后停止；
  - `blocked` 等待用户，用户回复后继续；
  - 暂停后不再开新一轮，继续后接着做；
  - 结束会中断当前这一轮；
  - 达到最多轮数后停止；
  - 一轮失败后转为已暂停；
  - 执行中用户发的消息进入下一轮输入；
  - 重启后转为已暂停。
- **6b 浏览器测试**：
  - 选自动化 → 设定目标和轮数 → 看到目标面板与轮数变化 → 暂停 / 继续 → 完成后显示总结；
  - 切到别的会议时，侧栏角标和"后台任务"出现，点击跳回；
  - 英文界面文字正确。
- **真实模型**（`AGENTS.md`，用户 2026-10-08）：用 OpenCode Go 的 `deepseek-v4.1-flash` 跑一个真实目标。例如："读项目里的 CSV，用 Python 做描述统计并出一张图，把结论写进项目日志，完成后汇报"。
  - 确认它连续多轮、跑了脚本、改了日志（日志留下历史版本），并在完成时调用了 `goal_update`；
  - 另跑一次中途暂停再继续；
  - 报告请求数和 token。
- 每步都在干净检出上跑 `npm run check` 通过；Windows 上同样通过。
- 原生：目标面板和侧栏后台任务在 100% / 125% 缩放下各截一张图，与旧界面对比。
- 有空的话补验中文输入法完整候选提交（M1 遗留）。
