# R4-7d 版本说明的用量与准确度

- 起草：Claude，2026-10-12。来源：R4-7 审阅。
- 执行：Sol；审阅：Claude。约 1–2 小时，一步交付。M2 之前完成。

## 问题

R4-7b 用真实 `deepseek-v4.1-flash` 自动整理了两次版本说明，见 `DESKTOP_IMPLEMENTATION.md` 2026-10-12 R4-7b 条。

**用量：**
- 第一次：19 次请求、207 万 tokens；
- 第二次：28 次请求、467 万 tokens。
- 整理一份说明要几百万 tokens，用户承受不了。

**质量：**
- 第一次把文件名里的省略号当成内容被截断；
- 第二次漏掉一处已核实的修改（社会 / 环境刺激），并且声称只改了一处。

## 原因（Claude 审阅时读代码判断，请先核实）

`app/services/versions/organizer.js` 一次发给秘书的内容：
- `changes`：完整的逐词比较结果。包括全部未改动的文字，并以逐段对象的 JSON 数组形式发送。
- 导图完整 JSON、计划全文。
- 本项目所有会议的完整纪要。

同时开放了工具。模型会再分段重读原文，而每次请求都把上面这一大包重发一遍，所以请求次数乘以输入大小就是几百万 tokens。

## 要做的

1. **只发改动，完整发。**
   - 把比较结果整理成可读的文本：每处改动带段落号，并带前后各一两句上下文。删除和新增用清楚的标记，例如 `[-旧-]{+新+}`。
   - 所有改动都要给出，一处都不能少，所以这不是截断。
   - 没改动的正文不发，只说明"其余第 N–M 段未改动，可用 `workspace_read` 按段读取"。这符合原则 4："只保留会说明省略了什么、并能分页读取的资源边界"。
2. **研究上下文只发要点：**
   - 纪要的目标与待办（复用 R4-5 助手概览里提取目标 / 待办的做法）；
   - 计划条目；
   - 导图节点的标题和层级（不发完整 JSON）；
   - 本项目最近更新的纪要优先。
3. **工具照常开放，提示改为"只在某处改动有歧义时读原文"。** 确认一份典型的稿件修订（例如两版各约一万字、几十处改动）能在 1–3 次请求内完成。
4. **针对两个质量问题：**
   - 改动摘要的开头列出"共 N 处改动，位于第 … 段"，让模型不能说成"只改了一处"；
   - 文件名等元数据和正文分开发送，不放进比较文字里。
5. 不改说明的三部分结构、模板和界面。

## 可以改的

`app/services/versions/organizer.js`、`comparison.js`、`template.js`（只改指令）、`app/services/assistant/overview.js`（如需复用提取目标 / 待办的函数，可以把它移到共用位置），以及相关测试和 `DESKTOP_IMPLEMENTATION.md`（不超过 5 行）。

## 不做的

- 不设字数上限，不截断改动。
- 不关掉工具。
- 不改界面。

## 完成标准

- **服务测试**：
  - 发给秘书的输入包含全部改动与段落号，不包含未改动的整段正文；
  - 改动很多时一处不少；
  - 文件名不进入比较文字。
- **真实模型**：用同样两份真实稿件，按 R4-7b 的方式再跑两次，报告每次的请求数和 tokens。
  - 目标：每次在 3 次请求以内、10 万 tokens 以内（这是本任务的验收目标，不是产品里的上限）。
  - 确认三部分齐全，上次的两个质量问题不再出现。
  - 如果做不到，报告原因，不要硬凑。
- 干净检出上跑 `npm run check` 通过；Windows 上同样通过。
