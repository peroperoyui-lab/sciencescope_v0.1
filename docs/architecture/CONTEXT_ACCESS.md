## 2. 结论：同一套机制，区别只在"范围"和"自动推送什么"

所有角色共用：同一组只读查阅工具、同一个上下文装配函数、同一份查找规则。每个角色只在一张**范围表**里不同：

| 角色 | 每轮自动推送 | 工具可查的范围 |
|---|---|---|
| 主专家 | 项目简报 + 查找规则（现有） | 本对话 + 本项目 |
| 专家 | 纪要 + 其后原文（现有） | 本对话 + 本项目 |
| 任务秘书 | **跟进包**：自它上次作答以来主对话的进展（见 §3） | 所属主对话 + 该项目 |
| 全局助手 | **工作区概览**（仅在变化时推送，见 §4） | 所有项目的主对话（含专家回答）、纪要、日志、计划、导图、版本；工具参数可指定 `projectId` / `chatId` |

所有角色都**不可见**：
- 临时对话；
- 其他助手的私聊；
- 研究资料库里的私有条目；
- 工具调用、工具结果、前导语（与 2.5 的可见性规则一致）。

范围只由会话决定：除全局助手可以在自己的范围内指定目标外，模型参数不能扩大范围。

## 3. 任务秘书：自动跟进，而不是等人喂

- **游标**：表 `context_cursors` 记录秘书读到主对话第几条（`seen_ordinal`）、读过纪要的哪一版及状态哈希；目标由 `assistant_conversations` 的秘书所有关系校验。
- **每次用户给秘书发消息时**，在消息前附一个跟进包。算法与专家的前文相同，起点换成游标：
  - 游标之后的新消息不多（默认 ≤ 6 万字符）：逐字附上这些新消息；单条 6 万字符以上但未超过安全边界的消息仍完整保留；
  - 太多（长任务里一直没用秘书）：最多等待 60 秒让纪要补齐，附上最新纪要与其后的原文；总安全边界为 24 万字符，超出时逐条列出省略编号并说明可用 `chat_recall` 读取，不静默截断；
  - 另附一行工作站状态（见 §5），仅在变化时附。
- 发送成功后才推进游标。跟进包进入秘书自己的 DSH 历史，只推送一次，由 DSH 的压缩机制负责长期保存。所以成本只和"新增了多少"有关。
- **用户直接提问**（不选中文本）时，秘书已经知道最新进展，细节自己用 `chat_recall` 回查。
- 选中文本"添加至秘书"的引用功能保留，作用是指明"就问这一句"。原"引用对话"摘录（20 条截断）不再需要，入口去掉或改为"以此对话为准"（只对全局助手有意义）。
- 秘书的查找规则放在**规则节**，不写进人设。人设是用户可编辑的，规则节随应用升级更新（见 §6）。这一节要写明：
  - 纪要是你（秘书）持续维护的记录；
  - 用户修改过的版本优先；
  - 你可以回查，也可以让纪要立即更新。

## 4. 全局助手：概览推送 + 按需下钻

- **工作区概览**（小，约 1–3k token）：
  - 每个项目：名称、工作文件夹、最近活动时间、纪要最新一版的"目标 / 待办"两栏摘要、未完成计划数、导图进度；
  - 每个项目最近 3 个对话的标题。
  - 表 `context_overview_cursors` 按全局助手会话保存哈希，只在变化时推送完整有界概览，不每轮全量推送；查询参数用于检索下钻。
- 需要细节时，用同一组工具指定目标下钻：
  - `workspace_overview()`；
  - `project_memory({projectId, section})`；
  - `chat_recall({chatId, query | from/to})`；
  - `research_search`（范围扩大到所有项目，私有条目仍不可见）。
- 以后项目很多时，概览只列最近活跃的 N 个，其余靠 `workspace_overview({query})` 检索。

## 5. 对话进度与工作站状态

**对话进度**（用户说的"table 的进度"）由两部分组成：
- 纪要：讲清楚整段对话走到了哪一步；
- 跟进包：从秘书上次读到的位置到现在的新消息（§3）。

秘书的规则节要求它：
- 回答"现在进行到哪了"一类问题时，先看跟进包和纪要的"已定结论 / 未决问题 / 待办"；
- 纪要落后于对话时，用 `chat_recall` 读纪要之后的原文，不凭印象回答。

跟进包开头写明位置，例如"主对话共 N 条，纪要覆盖到 #T，你已读到 #S"，让秘书一眼知道自己缺了哪一段。

**工作站状态**是补充，新增 `project_memory({section:"status"})`，返回紧凑的项目状态：
- 导图节点及其进度标记、未完成计划；
- 最近 5 条日志；
- 最新稿件版本及其说明状态；
- 纪要的待办栏。

秘书的跟进包和全局助手的概览都用这一份状态（同一个函数），专家也能查。
各分项（`log`、`plans`、`map`、`versions`）保留，用于看全文。

## 6. 解耦：以后加资料、加触发、改提示词都不动核心文件

1. **事件总线** `scripts/host-events.mjs`：
   - 宿主只发出事件：`chat.turn.persisted`、`discussion.finished`、`workbench.changed`、`version.stored`、`chat.idle`、`assistant.opened`、`project.entered`、`project.left`、`app.started`；
   - 纪要、跟进游标、记忆整理（T09）、概览缓存都**订阅**事件，不再由 `desktop-api.mjs` 直接调用。
   - 新增一种后台工作 = 新增一个订阅者。
2. **资料源注册表** `scripts/context/sources/*.mjs`：
   - 每个资料源（对话原文、纪要、日志、计划、导图、版本、状态、工作区）导出 `{id, sections, describe(role), read(scope, args)}`，实现位于 `scripts/context/registry.mjs` 与 `scripts/context/sources/`；
   - 工具参数的枚举和查找规则的文字都从注册表生成。
   - 新增一种资料 = 新增一个文件。
3. **范围表** `scripts/context/policy.mjs`：§2 的表格是数据，不是散落在各处的 `if (role === …)`；秘书只能访问其绑定的 Main/项目，全局助手才能选择目标。
4. **工具清单由宿主下发**：
   - DSH 适配器（`session-control.mjs`）启动时向宿主取工具清单（名称、描述、参数 schema），逐一注册为转发 `/host-call` 的工具；
   - 适配器本身不再写死任何研究工具。
   - 以后改工具描述或加工具，只改宿主，不改适配器，也不受 DSH 升级影响；清单与查找规则带 context API `t17.1` 版本。
5. **规则节与人设分开**：
   - 查找规则、跟进包格式按版本号存为规则节，经 `configureBrief`（与项目简报同一机制）在每轮前按需刷新。
   - 应用升级后，已有会话下一轮就用上新规则，不会覆盖用户编辑过的人设，也不会像 `role_prompt_receipts` 那样把旧规则冻结在会话里。
6. **契约与存储**：
   - 工具名和参数只增不改（`contextApi` 版本号写进规则节）；
   - 新表 `context_cursors` 与 `context_overview_cursors` 用 `CREATE TABLE IF NOT EXISTS`，升级时数据保留；工具不得暴露工具调用/结果、临时对话、助手私聊或资料库私有条目。

## 7. 总结：按规则触发，设置可调（用户修订 2026-09-26）

**T18 已通过本任务验收。** T17 已提供查阅、跟进和概览装配；当前不恢复每轮主对话后的无条件纪要总结。讨论结束、手动刷新、秘书跟进积压超过 6 万字符时补齐仍可用；按消息数/token、进入/离开项目的持久化设置和后台订阅已由 `summary-policy.mjs` 接入。当前分支 `codex/t18-summary-policy-20260927` 叠加已推送 T17 `5ea220f`。全量 `npm test` 180/180、22 项浏览器/API smoke、12 张截图及第三轮真实模型评测通过；root 已复核设置/提议界面及英文深色纪要窗口。原生客户端未重测。

每轮主对话后都总结会占用大量用量。纪要的更新只在下列时机进行，全部可在 设置 → 任务秘书 → 自动总结 中调整：

| 时机 | 默认 | 说明 |
|---|---|---|
| 有序讨论结束后 | 开 | 讨论产出多、次数少 |
| 每 n 条主对话消息 | 开，n = 20 | 从纪要覆盖的位置起算，用户消息和回答都计数 |
| 每 n 个新 token | 开，n = 30 000 | 按纪要之后新消息的估算 token 计；达到此阈值会触发总结，但不是原文硬截断上限，实际内容可能超过阈值且不会静默截断 |
| 进入项目时 | 开 | 打开该项目的对话时补齐上次遗留的部分；没有新内容时不调用模型 |
| 离开项目时 | 开 | 切换到别的项目或关闭应用时补齐。关闭应用不等待，记为"待补"，下次启动后执行 |
| 手动"让秘书更新" | 始终可用 | 纪要窗口中的按钮 |
| 秘书被提问且积压过多 | 始终 | 跟进包需要（§3）；只在积压超过 6 万字符时触发 |

- 几个时机同时满足时只运行一次；每次只处理新增部分。
- 没有新内容时，任何时机都不调用模型。
- 默认仍为：讨论后开启、每 20 条消息、每 30000 个估算 token、进入/离开项目开启、Markdown 导出开启；工作站四项默认 `off`。设置保存在 `secretary_preferences.summary_json`，阈值范围为消息 4–500、token 2000–500000。
- `summary-policy.mjs` 订阅宿主事件；Main 回合与讨论使用纪要服务的防抖调度，项目切换按对话串行补齐，启用离开项目规则时关闭写入 `summary_pending`，启动后延迟 30 秒处理。`focus(projectId)` 立即返回并在后台发出切换事件。

**总结的范围**：
- **纪要**（每个对话一份）：
  - 始终更新，记录项目进度和该对话的信息（目标、结论、否决、分歧、立场、文稿与文件、待办）；
  - 同时可以保存为项目文件夹中的 Markdown 文件（默认开）。
- **随总结一起更新的工作站内容**：导图、稿件版本说明、计划、日志，各自有开关，**默认全部关闭**。
  - 设置旁的"i"提示写明：这些内容有大量用户参与，非必要不开启。
  - 每项可选：关闭 / 提议（秘书生成修改建议，用户逐条确认后写入） / 直接更新。
  - 直接更新也有边界：
    - 日志只追加；
    - 计划只新增或勾选完成；
    - 导图只改节点状态标记、只新增标注为"秘书添加"的子节点，不改写、不删除用户写的节点；
    - 版本说明只为还没有说明的版本整理（沿用现有的版本整理）。
  - 每次写入都记录来源（哪一版纪要），可以撤销。
- 当前实现采用提示中的 JSON 格式加服务端严格 allowlist 校验；当前 DSH host 尚未提供可宣称的原生 JSON Schema constrained-generation，因此不把提示约束写成运行时安全边界。导图新增子节点带 `origin: 'secretary'`，桌面工作站已显示“秘书添加”。

**成本关系**：总结触发得越少，专家和秘书收到的"纪要之后原文"通常越长。"每 n 个新 token"是触发总结的估算阈值，不是原文的硬截断上限；实际内容可能超过该阈值，系统不会因达到它而静默截断原文。用户可通过调整触发频率，在总结调用与后续上下文长度之间取舍。
