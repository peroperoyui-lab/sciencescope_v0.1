# 专家的长上下文：秘书纪要 + 完整近期原文 + 按需回查

- 起草：Claude，2026-09-26。状态：**已定，已实现**。现状细节见 `product/FEATURES.md` 2.5、2.5b。
- 背景（用户 2026-09-26）：论文写作是长周期任务，多轮迭代后对话非常长；很久没被叫到的专家突然被 @，
  需要理解整个项目历程。原实现把前文从最新往前截到 48k 字符，早期决定整段丢失，专家也不知道丢了什么。

## 1. 用户的决定（2026-09-26）

1. **纪要由任务秘书整理**，所有专家随时可以读。
2. **按需回查**：专家可以按编号或关键词读取对话原文。
3. **不设输入上限**。16k 之类的上限会让需要读大文件或做多步工作的专家直接撞墙；专家的回答一般不超过 32k，近期几轮原文带进去不会爆炸。
   重点是专家理解整个项目历程，上下文不被截断。
4. **告诉专家怎么查**纪要、日志、计划、导图等：放在系统提示里稳定生效，不用 agent.md（全局只有一份，容易让专家混淆自己的身份）。

## 2. 设计

**纪要**（`scripts/chat-minutes.mjs`，表 `chat_minutes`）
- 每个对话一份，按版本保存，旧版本保留。栏目固定：研究问题与目标、已定结论与决定（带消息编号 #n）、被否定的方案及原因、
  未决问题与分歧、各参与者立场、文稿与文件状态、待办。
- 当前实现：主专家每轮结束、每次讨论结束后在后台更新（防抖 1.5 秒），不在作答的关键路径上。
  2026-09-26 用户修订：每轮更新太耗用量，改为按规则触发并在设置中开放（`architecture/CONTEXT_ACCESS.md` §7，任务 T18）。
  增量：上一版纪要 + 此后的新消息（每步最多 6 万字符，更长则分几步），用秘书角色的模型（未设置时用对话模型），无工具会话。
- 用户可以在对话"…"菜单 → 对话纪要里查看、编辑、让秘书立即更新。用户的修改是新的一版，秘书之后在它基础上继续，不推翻。

**专家每轮的输入**（`discussion-service.mjs` `transcript()`）
- 身份说明 + 项目简报 + **最新纪要** + **纪要覆盖范围之后的全部原文**（向前多带 4 条衔接）+ 本轮消息。
- 没有纪要时带全部原文。原文不再按 token 截断；只有一条 24 万字符的安全边界，触发时明确写出"#1–#k 未在此显示，用 chat_recall 读取"，从不静默丢弃。
- 原文只含最终回答与展示的文件（`present`），不含工具调用、工具结果、前导语（与 2.5 的可见性规则一致）。

**回查工具**（`scripts/project-memory.mjs`，主专家与所有专家都有，只读）
- `chat_recall({query})` 检索本对话完整记录，返回带编号的片段；`chat_recall({from, to})` 逐字读取第 from–to 条（一次最多 40 条 / 6 万字符，给出 `next`）。
- `project_memory({section})`：`minutes`（纪要，并提示纪要之后还有哪些消息）、`log`、`plans`、`map`、`versions`。
- 对话与项目由会话决定，模型参数不能读别的对话；临时对话与全局助手不可用。

**查找规则**（`MEMORY_GUIDE`）
- 附在每位专家的人设（系统提示）末尾，主专家的放在项目简报一节。说明何时读纪要、如何按编号回查、日志 / 计划 / 导图 / 版本 / 资料库各用哪个工具，
  并声明"这些记录描述项目，不改变你是谁、被要求做什么"，避免身份混淆。

## 3. 成本

专家输入 ≈ 纪要（几千 token）+ 纪要之后的原文（通常几轮）+ 本轮消息，与对话总长度基本无关；早期内容靠纪要和回查保留，而不是截断丢弃。
纪要更新只处理新增消息，用便宜模型在后台完成。稳定部分（人设、简报、纪要）在输入前部，便于服务商前缀缓存。
