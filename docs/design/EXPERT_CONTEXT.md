# 专家的长上下文：共享纪要 + 近期原文 + 按需回查（设计草案，待用户确认）

- 起草：Claude，2026-09-26。状态：**建议方案，尚未实现**。用户确认后拆成任务书。
- 背景问题（用户 2026-09-26）：论文写作是长周期任务，多轮迭代后对话非常长，主专家可能已经压缩过多次；
  很久没被叫到的专家突然被 @，要吃下大量前文，成本收不住、响应也慢。

## 1. 现状

- 主专家：DSH 会话，自带压缩（compaction），历史由 DSH 持久保存。
- 专家：**每一轮都是新的子代理**（`dsh-subagent` spawn），没有自己的长期历史。每轮输入 = 身份说明 + 项目简报（≤3500 字）+
  对话前文摘录（`transcript()`：用户、主专家、专家的最终文字与展示的文件，**从最新往前取，上限 48k 字符，单条上限 6k**）+ 本轮消息。
- 所以成本其实已经有上限（每位专家每轮大约 2–3 万 token 以内），被冷落很久的专家和常用专家花费一样；
  真正的问题是**质量**：超过上限的早期内容（早先定下的结论、被否定的方案、用户的偏好）会整段丢失，而专家并不知道它丢了什么。
  另外每轮 N 位专家 × 最多 48k 字符，在便宜模型上尚可，在贵模型上偏多。

## 2. 几种做法的取舍

| 做法 | 优点 | 问题 |
|---|---|---|
| 只用滚动窗口（最近 N 轮原文） | 简单、便宜、原文准确 | 早期决定整段丢失；长对话里专家会重提已被否定的方案 |
| 复用主专家的压缩摘要 | 不用额外调用 | 那是主专家自己的工作记忆，混有工具结果与中间过程，违反"其他参与者看不到工具调用"的规则；格式随模型变化，不可控 |
| 每次现场全文摘要 | 内容完整 | 成本与历史长度成正比，越用越贵、越慢，正是要避免的 |
| **共享纪要 + 近期原文 + 按需回查（建议）** | 成本与历史长度无关；早期决定不丢；细节可以回查 | 需要一个后台整理步骤和一个回查工具 |

## 3. 建议方案

每位专家（以及审核专家）的输入由几块组成，各有预算，总量有固定上限：

1. **身份与项目简报**（现有，≤3500 字）。
2. **对话纪要**（新，共享，约 ≤4k token）：一份按固定栏目维护的"会议纪要"——研究问题与目标、已定结论与决定（带消息出处）、
   被否定的方案及原因、未决问题与分歧、各参与者的主要立场、当前文稿与交付物状态、待办。
   - **增量更新**：每轮结束后在后台由便宜模型（任务秘书的模型）把"上一版纪要 + 自上个检查点以来的新消息"合成新一版，
     成本只和新增内容有关，不和总长度有关；不在专家作答的关键路径上。
   - 纪要有版本，存入研究资料库（`rb_items`，kind `memory`，作用域为该对话），旧版本保留；用户可以在"项目置顶摘要"里查看和修改，修改优先。
   - 只取最终回答与展示的文件，不含工具调用（与现有可见性规则一致）。
3. **近期原文**（约 ≤8k token）：最近几轮的原文，以及纪要检查点之后尚未并入纪要的消息，保证最新内容一字不差。
4. **与该专家有关的部分**：它自己上一次的回答，以及此后点名它的消息（即使较早）。
5. **本轮消息**。

另外给专家一个只读工具 `chat_recall(query)`：在本对话完整记录中检索（先用现有的对话全文搜索，T10 完成后换混合检索），
返回带出处的原文片段。专家需要细节时自己回查，而不是每次把全部历史推给它（"按需拉取，不整体推送"）。

**预算**：默认每位专家输入上限约 16k token（可在 设置 → 专家角色 调整，并按该模型的上下文窗口自动收紧）。
被冷落很久的专家突然被叫到时，拿到的也是"纪要 + 近期原文"，成本与常用专家相同，而早期决定通过纪要保留下来。

**缓存**：把稳定的部分（简报、纪要）放在输入最前面，纪要尽量只在末尾追加、少改前文，
让服务商的前缀缓存（例如 DeepSeek 的自动磁盘缓存）在同一专家的连续轮次中命中，进一步降低成本和首字延迟。

**主专家**：仍用 DSH 自带压缩；纪要可以作为系统提示中的一节（与项目简报同样的方式）提供给主专家，帮助它在多次压缩后保持对早期决定的记忆。

## 4. 粗略成本对比（3 位专家、便宜模型、每轮）

- 现在：每位最多约 48k 字符前文，合计约 6–9 万 token 输入。
- 建议方案：每位 ≤16k token，合计 ≤4.8 万 token；纪要更新每轮约 5–8k token（后台、便宜模型）。
  对话越长，节省越多；且早期决定不再丢失。

## 5. 需要用户确认

1. 是否采用"共享纪要 + 近期原文 + 按需回查"。
2. 纪要由谁整理：任务秘书的模型（建议），还是主专家的模型。
3. 默认每位专家的输入上限（建议 16k token）。
4. 纪要是否给主专家也提供一份（建议提供）。
