# 各角色的上下文：一套机制，按角色划定范围（任务秘书、全局助手）

- 起草：Claude，2026-09-26。状态：**建议方案**。实现任务：`docs/tasks/T17_context_access_layer.md`（后端 Astra，界面 Claude）。
- 前置：`design/EXPERT_CONTEXT.md`（秘书纪要、`chat_recall` / `project_memory`、专家输入不截断，已实现）。
- 用户问题（2026-09-26）：
  - 全局助手要能看到各处对话的回答、日志、计划等内容；
  - 秘书的总结什么时候触发；
  - 长任务中一直没用秘书，它没有当前对话的上下文，直接提问时怎么回答；
  - 它怎么看工作站的进度；
  - 能否和专家用同一套机制；
  - 系统要高度解耦，方便以后推送更新。

## 1. 现状与问题

| 角色 | 自动得到的上下文 | 可用的查阅工具 | 问题 |
|---|---|---|---|
| 主专家 | DSH 自己的历史（带压缩）+ 项目简报 + 查找规则 | `chat_recall`、`project_memory`、`research_*` | — |
| 专家 | 纪要 + 纪要之后的全部原文 + 查找规则 | 同上 | — |
| 任务秘书 | 只有用户手动"引用对话"时的摘录（最近 20 条，每条截到 3000 字，共 2 万字） | 技术上已注册同样的工具（范围是它所属的主对话），但人设写着"只用明确提供的上下文"，也没有查找规则，所以实际上不会用 | 长期不用时对主对话一无所知；摘录截断，违背"不截断"的决定 |
| 全局助手 | 同上（可引用任意对话） | 查阅工具对它全部拒绝 | 看不到其他项目的回答、日志、计划 |

另有两处耦合：
- 纪要在 `desktop-api.mjs` 里被直接调用（`minutes.schedule`）；
- 工具的 schema 写死在 DSH 适配器 `session-control.mjs` 里。

以后每加一种资料或一个触发时机都要改这几处核心文件，推送更新时容易牵一发动全身。

## 2. 结论：同一套机制，区别只在"范围"和"自动推送什么"

所有角色共用：同一组只读查阅工具、同一个上下文装配函数、同一份查找规则。每个角色只在一张**范围表**里不同：

| 角色 | 每轮自动推送 | 工具可查的范围 |
|---|---|---|
| 主专家 | 项目简报 + 查找规则（现有） | 本对话 + 本项目 |
| 专家 | 纪要 + 其后原文（现有） | 本对话 + 本项目 |
| 任务秘书 | **跟进包**：自它上次作答以来主对话的进展（见 §3） | 所属主对话 + 该项目 |
| 全局助手 | **工作区概览**（仅在变化时推送，见 §4） | 所有项目的主对话（含专家回答）、纪要、日志、计划、导图、版本；工具参数可指定 `projectId` / `chatId` |

所有角色都**不可见**：
- 临时对话；
- 其他助手的私聊；
- 研究资料库里的私有条目；
- 工具调用、工具结果、前导语（与 2.5 的可见性规则一致）。

范围只由会话决定：除全局助手可以在自己的范围内指定目标外，模型参数不能扩大范围。

## 3. 任务秘书：自动跟进，而不是等人喂

- **游标**：记录秘书读到主对话第几条（`seen_ordinal`）、读过纪要的哪一版。
- **每次用户给秘书发消息时**，在消息前附一个跟进包。算法与专家的前文相同，起点换成游标：
  - 游标之后的新消息不多（默认 ≤ 6 万字符）：逐字附上这些新消息；
  - 太多（长任务里一直没用秘书）：附上最新纪要，加上纪要覆盖之后的原文，并说明 #a–#b 可用 `chat_recall` 读取；
  - 另附一行工作站状态（见 §5），仅在变化时附。
- 发送成功后才推进游标。跟进包进入秘书自己的 DSH 历史，只推送一次，由 DSH 的压缩机制负责长期保存。所以成本只和"新增了多少"有关。
- **用户直接提问**（不选中文本）时，秘书已经知道最新进展，细节自己用 `chat_recall` 回查。
- 选中文本"添加至秘书"的引用功能保留，作用是指明"就问这一句"。原"引用对话"摘录（20 条截断）不再需要，入口去掉或改为"以此对话为准"（只对全局助手有意义）。
- 秘书的查找规则放在**规则节**，不写进人设。人设是用户可编辑的，规则节随应用升级更新（见 §6）。这一节要写明：
  - 纪要是你（秘书）持续维护的记录；
  - 用户修改过的版本优先；
  - 你可以回查，也可以让纪要立即更新。

## 4. 全局助手：概览推送 + 按需下钻

- **工作区概览**（小，约 1–3k token）：
  - 每个项目：名称、工作文件夹、最近活动时间、纪要最新一版的"目标 / 待办"两栏摘要、未完成计划数、导图进度；
  - 每个项目最近 3 个对话的标题。
  - 只在变化时推送差异，不每轮全量推送。
- 需要细节时，用同一组工具指定目标下钻：
  - `workspace_overview()`；
  - `project_memory({projectId, section})`；
  - `chat_recall({chatId, query | from/to})`；
  - `research_search`（范围扩大到所有项目，私有条目仍不可见）。
- 以后项目很多时，概览只列最近活跃的 N 个，其余靠 `workspace_overview({query})` 检索。

## 5. 工作站进度（"table 的进度"）

新增 `project_memory({section:"status"})`，返回紧凑的项目状态：
- 导图节点及其进度标记、未完成计划；
- 最近 5 条日志；
- 最新稿件版本及其说明状态；
- 纪要的待办栏。

秘书的跟进包和全局助手的概览都用这一份状态（同一个函数），专家也能查。
各分项（`log`、`plans`、`map`、`versions`）保留，用于看全文。

## 6. 解耦：以后加资料、加触发、改提示词都不动核心文件

1. **事件总线** `scripts/host-events.mjs`：
   - 宿主只发出事件：`chat.turn.persisted`、`discussion.finished`、`workbench.changed`、`version.stored`、`chat.idle`、`assistant.opened`；
   - 纪要、跟进游标、记忆整理（T09）、概览缓存都**订阅**事件，不再由 `desktop-api.mjs` 直接调用。
   - 新增一种后台工作 = 新增一个订阅者。
2. **资料源注册表** `scripts/context/sources/*.mjs`：
   - 每个资料源（对话原文、纪要、日志、计划、导图、版本、状态、工作区）导出 `{id, sections, read(scope, args)}`；
   - 工具参数的枚举和查找规则的文字都从注册表生成。
   - 新增一种资料 = 新增一个文件。
3. **范围表** `scripts/context/policy.mjs`：§2 的表格是数据，不是散落在各处的 `if (role === …)`。
4. **工具清单由宿主下发**：
   - DSH 适配器（`session-control.mjs`）启动时向宿主取工具清单（名称、描述、参数 schema），逐一注册为转发 `/host-call` 的工具；
   - 适配器本身不再写死任何研究工具。
   - 以后改工具描述或加工具，只改宿主，不改适配器，也不受 DSH 升级影响。
5. **规则节与人设分开**：
   - 查找规则、跟进包格式按版本号存为规则节，经 `configureBrief`（与项目简报同一机制）在每轮前按需刷新。
   - 应用升级后，已有会话下一轮就用上新规则，不会覆盖用户编辑过的人设，也不会像 `role_prompt_receipts` 那样把旧规则冻结在会话里。
6. **契约与存储**：
   - 工具名和参数只增不改（`contextApi` 版本号写进规则节）；
   - 新表（`context_cursors`）用 `CREATE TABLE IF NOT EXISTS` 并登记迁移，升级时数据保留。

## 7. 总结（纪要）的触发时机

纪要已经是自动的，不需要用提示词触发。完整的触发表由事件总线登记：

| 事件 | 后台工作 | 状态 |
|---|---|---|
| 主专家一轮结束、讨论结束 | 纪要增量更新（防抖 1.5 秒） | ✅ 已实现（改为订阅事件） |
| 用户打开秘书面板、给秘书发消息 | 纪要落后于主对话时先补齐，再生成跟进包 | T17 |
| 对话空闲 N 分钟 | 从纪要的新增部分提议长期记忆（进收件箱，用户确认） | T09（改为基于纪要） |
| 稿件新版本 | 版本说明整理（已有） | 改为订阅事件 |
| 用户点"让秘书更新" | 纪要立即更新 | ✅ |
