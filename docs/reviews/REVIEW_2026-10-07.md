## 2. 离 alpha 还差什么

alpha 的标准（`ROADMAP.md`）：在 Windows 候选安装包上走完一次真实研究流程；退出后没有残留进程；升级后数据完整；卸载默认保留数据；签名可以核查。

| 阶段 | 剩余工作 | 说明 |
|---|---|---|
| R4 | R4-11（进行中）、R4-5、R4-2、R4-6、R4-7、R4-8、R4-9、R4-10，然后 M2 | 复原旧功能 |
| M1 | 中文输入法完整候选提交 | 唯一遗留项 |
| R5 | 旧数据导入、全量导出、原生外壳默认启动新核心、删除旧线、改写 `SYSTEM_SPEC.md` 里的旧线技术段落 | 切换 |
| R6 | NSIS 安装包（自带 Node、uv、Python）、数据目录与升级不覆盖、更新通道、alpha.1 → alpha.2 升级演练、最低配置检测 | 打包 |
| 签名 | 需要用户提供证书或签名服务 | 外部依赖，目前阻塞 |
| C | 用候选包做真实内测，阻塞问题清零 | alpha 门槛 |

**建议：划一条 alpha 必需线**，避免 R4 全部做完才开始打包。

- **alpha 必需**：
  - R4-11、R4-5 全局助手、R4-2 研究输入；
  - R4-8 Python：分析流程离不开；
  - R4-7 文献版本：写作流程需要，而且和 §5 的写作工作台有关；
  - 再加 R5、R6。
- **可以放到 alpha 之后**：R4-9 插件与技能、R4-10 导图图片。旧版都有，但不影响研究主流程。
- **需要用户决定**：
  - R4-6 的"询问 / 完全接管"是审批开关，和原则 5"不加审批"有冲突，"自动化"（朝目标连续工作）则是独立功能。
  - 建议：alpha 只做"自动化"，审批两档按原则 5 不做；或者保留"询问"作为用户自己的偏好。

R6 可以和 R4 后半段并行：打包和升级演练不依赖剩余功能，可以交给 Dot 先在现有版本上演练。

## 3. 后端代码工整度与解耦

### 3.1 量化

| 项 | 数值 |
|---|---|
| 非测试代码 | core 2,651 行；services 7,238；server 722；runtime 820；ui 8,918（不含译文） |
| 测试代码 | 6,967 行，132 项测试（2 项仅 Windows） |
| 最大源文件 | `meeting.js` 487 行、`settings.js` 475、`workbench.js` 474、`actions.js` 451、`turn-runner.js` 450、`secretary/minutes.js` 433 |
| `any` 类型 | 180 处（services 72、ui 68、core 25） |
| 绕过检查 | 2 处，都有理由（DSH 插件 API 类型、控制字符正则） |
| 旧线改动 | `v0-prototype` 之后 `desktop/`、`scripts/`、`adapters/` 零改动 |

### 3.2 做得好的

- **分层方向全部正确。**
  - core 不引用 services / server / ui / runtime；
  - services 不引用 server / ui；
  - ui 不引用任何后端模块；
  - DSH 只在 `app/runtime/` 里出现，运行时接口 `port.js` 只有 46 行。
- **组装集中**：`app/app.js` 一处显式注入所有服务，没有全局单例；测试可以换掉运行时。
- **路由很薄**：server 一共 722 行，只做解析和转发。
- **数据升级**：
  - 迁移 001–007 编号齐全，每次迁移前备份，每个迁移都有升级测试。
  - 后续加功能走新迁移即可，旧数据不会丢。
- **一套工具**：所有角色共用 6 个工具（`research_search/read`、`workspace_read/edit/undo`、`propose_main_draft`），没有按角色分权限表，符合原则 2。

### 3.3 需要整理的（建议在 R4-5 / R4-6 之前做）

1. **`turn-runner.js` 在变成"什么都管"的文件。**
   - 现状：450 行。除了跑一轮发言，还从外面接收 4 个回调（纪要覆盖范围、纪要已覆盖的消息、秘书跟进包、项目简报），自己拼装上下文。
   - 风险：R4-5（助手跨项目查阅）和 R4-6（自动化连续发言）都会再往这里加东西。
   - 建议：把"这位参与者这次能看到什么"抽成一个独立的上下文组装服务（`services/context-assembly.js`），由它调用 `core/context.js` 的纯函数和纪要、跟进、简报服务；`turn-runner.js` 只管会话、流式输出和收尾。工作量小，行为不变，现有测试即可验证。
2. **讨论状态仍在消息的 `refs` JSON 里。** 共 12 处读写 `refs.discussion`。R4-4 已经改用建表，这里是 R4-3 留下的；R4-6 如果还要加状态，先迁移成列。
3. **代码风格的一致性。**
   - 45 处 JSDoc 参数压成一行，集中在 R4-1b、R4-3、R4-4 的新文件里。
   - `CODE_STYLE.md` 已经补了规则，但旧代码没改。可以在第 1 项的整理任务里顺手改掉，不单独开任务。
4. **`any` 偏多的地方**：资料库存储层和秘书服务。等第 1 项整理时，给对外的函数补上类型，内部不强求。
5. **`SYSTEM_SPEC.md` 过时**：§2 的技术实现大多仍描述旧线，新核心的现状分散在 `CORE_MODEL.md` 和各任务书里。R5 删除旧线时一并改写；在那之前，以 `CORE_MODEL.md` 为准。

### 3.4 后续更新的可行性

- **加功能**：新服务按现有模式写在 `app/services/<名字>/`，在 `app.js` 注入，路由一个文件，迁移一个编号。R4-1 到 R4-4 都是这样做的，没有改动别的模块的结构。可行。
- **换运行时**：只需要重写 `app/runtime/`，按 `docs/design/RUNTIME_PORT.md` 的契约实现。业务代码不用动。可行。
- **改界面**：组件按功能拆文件，状态集中在 `state.js`，各功能的动作分别放在 `*-actions.js`。可行；`meeting.js` 和 `actions.js` 接近 500 行，以后再加功能时就要拆。

## 4. 是否跑偏主线

**没有跑偏。** 产品的定位是"多位 AI 专家和用户一起讨论，按完整研究流程推进用户自己的项目"。这个核心已经在新核心上跑通：

- 资料库（R4-1）
- 多专家讨论（R4-3）
- 秘书纪要、指令草稿与记忆（R4-4）

主线始终是 R4 复原 → R5 切换 → R6 打包，没有加入主线以外的功能；你的新想法记在 `docs/idea.md`，标为 alpha 之后。

**要防的两个风险：**

1. **R4 全部做完才开始打包，alpha 会拖得很晚。** 按 §2 的建议划出必需线，R6 提前并行。
2. **想法进入当前开发。** 写作工作台和 WorkTeam 都是大功能，现在开始做会推迟 alpha。建议只在 R4-7（文献版本）的数据设计里给写作工作台留好接口（§5），其余等 alpha 之后。

## 5. 与新想法的衔接

写作工作台（见 `docs/idea.md`）依赖三样东西，现在的计划里已经部分具备：

- **稿件版本**：R4-7。

建议：在 R4-7 的任务书里，让稿件版本和段落 / 图表的"来源绑定"使用同一种引用格式（文件、脚本、数据、资料库条目），以后写作工作台直接复用，不必重做数据模型。别的不提前做。
