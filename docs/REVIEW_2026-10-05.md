## 用户定调（2026-10-05，优先于下文中与之冲突的建议）

- **初心**：ScienceScope 是一个整洁的"数据库 + harness"：多位专家交流、有完整流程的学术研究助手，帮助用户理解并推进自己的科研项目。
- **数据**：
  - 本地文件和文件夹，方便用户编辑；
  - 一个 SQLite，主要给智能体用，以及 RAG 向量。
  - 全部内容都放在安装目录里，包括项目、对话上下文、脚本等；只有用户选择的外部项目文件夹例外。
- **编辑**：界面上影响论文撰写的功能，秘书和全局助手基本都能编辑，比如工作台、日志、计划、框架。
- **角色**：秘书、全局助手、各位专家不需要差异化的功能和权限边界，本质都是"查项目、改数据"。
- **边界**：反感写死的输出上限和权限上限；提示词的软边界比硬边界更有效。
- **测试与安全**：不要过度测试、过度限制、过度保护。现阶段关注系统能不能跑起来、跑好、可读可维护，而不是安全。不做安全测试；围栏以后再加，或者不加，改为对各功能点做功能测试。

据此：

- 数据布局与角色模型见 `design/DATA_AND_ROLES.md`；

## 结论

1. **慢，主要慢在流程，而不是写代码。**
   - 规则、证据要求和交付报告越堆越多。T24 改动的行数里，文档 988 行，多于产品代码的 863 行。
   - 这套流程大部分是 Claude 定的，责任在 Claude。
2. **代码能用，但有四处结构性问题，越往后越贵：**
   - 前端靠逐层覆盖原型里的全局函数来接入功能；
   - 后端集中在一个上帝文件里；
   - 数据库没有统一的迁移机制；
   - 没有代码风格约束。
3. **"助手和秘书能编辑整个工作台"目前做不到。** 现有的四套提议 / 写入机制各管一摊，需要统一成一套。
4. **alpha 应该缩小范围。** 先补地基（流程、风格、数据迁移、统一编辑），再打包；其余功能放到 alpha 之后。

### B. 前端架构

- **现状**：生产界面 = 544 KB 原型 HTML + 约 55 个模块。模块用"保存原函数 → 重新赋值"的方式改写原型的全局函数：
  - `render` 被包了 2 层（`settings.mjs`、`workspace-layout.mjs`）；
  - `objectMenu` 被包了 3 层（`workspace.mjs`、`python-settings.mjs`、`memory-consolidation.mjs`）；
  - `submitMain` 被包了 2 层（`live-chat.mjs`、`discussion.mjs`）；`go`、`loadThread` 等也被包过；
  - 共有 353 处直接读写全局状态 `S` / `V`。
- **影响**：行为取决于脚本加载顺序，很难追踪。此前"晚到的 render 冲掉对话框""重绘丢失未保存设置"这类问题都来自这里。
- **改法**（渐进替换，不推倒重来）：
  1. 新增一个小的界面注册层（菜单项、设置页、消息渲染、路由），新功能一律通过注册接入，**禁止再新增包装**；
  2. 把现有的包装逐个改成注册；
  3. alpha 之后再把原型的渲染逐块迁成独立模块。视觉以原型为准，不变。

### C. 后端结构与代码风格

### D. 用户数据的升级连续性与可读性

| 问题 | 改法 |
|---|---|
| 60 张表由 24 个模块各自 `CREATE TABLE IF NOT EXISTS` 并临时 `ALTER TABLE`，没有统一的版本顺序 | 统一的迁移注册表：编号迁移、一个入口、记录在 `PRAGMA user_version` 或 `schema_migrations`；模块不再自己建表 |
| 升级前没有备份 | 迁移前自动做一致性备份（SQLite backup API），失败时回滚并提示 |
| 新数据被旧版本打开没有保护 | 数据库版本高于程序时拒绝写入，提示升级 |
| 存储分散：SQLite、`environments.sqlite`、项目文件夹里的 `workbench.json` 与 `mind_map/research.json`、DSH 会话日志、DSH `settings.yaml`、凭据 | 写 `docs/DATA_FORMAT.md`：每类数据存在哪、格式、版本、是否可读、如何导出 |
| 知识数据有两份（旧 `knowledge` 表与资料库 `rb_items` 镜像） | 迁移进资料库后，旧表只读、最终删除 |
| 模型上下文历史锁在 DSH 格式里 | T23 的中立导出（已有任务书） |
| 可读性 | 提供"导出全部数据"：Markdown 加 JSON，用户不依赖本程序也能读 |

Dot 的升级演练脚本（`scripts/rehearsal/`）作为每次发布前的门槛。

### E. 智能体编辑能力（用户要求）

- **现状**：
  - 写入路径有四套：
    1. `research_propose`（资料库收件箱）；
    2. 总结规则对导图、版本、计划、日志的 off / propose / apply（只能经由纪要总结触发）；
    3. 秘书 `propose_main_draft`；
    4. 记忆整理。
  - 图谱的 `graph_propose` 还在计划中；
  - 提议分散存在 `rb_proposals`、`summary_proposals`、`assistant_draft_proposals` 三张表里。
  - 全局助手和秘书**不能直接编辑**工作台、导图、计划、日志、版本说明、专家名册、笔记模板等。
- **目标**：工作台的所有用户可编辑对象，助手和秘书都能编辑，在各自的范围内（秘书限所属项目，全局助手覆盖所有项目）。
- **设计要点**（Claude 写设计文档 `design/WORKSPACE_EDIT.md`，Sol 实现）：
  1. **资源注册表**：每类对象（导图节点、计划、日志、版本说明、纪要、笔记模板、专家名册与人设、项目设置、资料库条目、图谱……）登记读、写操作和校验规则。
  2. **两个通用工具** `workspace_read` / `workspace_edit`，由宿主工具清单下发，范围由范围表决定。不再为每类对象单独做工具。
  3. **每类对象一个写入策略**：直接生效并可撤销，或者进收件箱等确认。
  4. **一套修订记录和撤销**，**一个收件箱**，取代现有三张提议表；旧数据迁移过去。
  5. **永远不开放给智能体的**：服务商与 key、受保护路径、执行策略与权限、数据目录。

## 四、新的工作方式（S0 写进 AGENTS.md 与任务书模板）

- **任务书**写明：目标、允许改动的文件、完成标准、明确不做的事；正常 1–2 小时的量，超出就停下报告。
- **默认验证**：开发中只跑相关测试；交付前跑一次 `npm run check`。
  - 动到界面的加一张截图；
  - 动到原生层的才做原生验收；
  - 真实模型评测只在评测任务里做。
- **报告** 15 行以内：做了什么、改了哪些文件、测试结果、遗留问题。长材料不进仓库。
- **审阅**：Claude 看 diff、跑测试；不再每出一次事故就加一条规则，能变成测试的变成测试。

## 五、代码风格基线（S1 写成 `docs/CODE_STYLE.md` 并由工具强制）

- **格式**：Prettier 统一，行宽 100，一行一条语句，禁止把多条逻辑压在一行。
- **文件**：单个文件建议不超过约 400 行，超过就按职责拆分；一个模块只做一件事。
- **命名**：完整单词。函数是动词短语，数据是名词。
- **注释**：说明为什么，不复述代码；对外函数写简短的 JSDoc（参数、返回值、错误）。
- **结构**：
  - 后端按领域分模块，路由只做参数解析和调用；
  - 数据库访问集中在各领域的 store 里，表结构变更只走迁移注册表；
  - 前端新功能只经注册层接入。
- **错误**：用带 code 的错误类型，面向用户的文字只在边界处产生。
- **依赖**：新增依赖要说明理由；不为测试新增框架。
