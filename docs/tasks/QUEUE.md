## 通用做法

1. **一次只做一批**。每批结束推送并报告，等用户或 Claude 确认后再开始下一批。
   - 批内遇到问题，Astra 自己判断：根因清楚、有回归测试的就直接修，修完继续，最后在报告里说明（2026-09-27 用户修订）。
   - 只有涉及产品取舍、或无法确定根因时才停下。
2. **一个任务一个分支**：`codex/tNN-<主题>-YYYYMMDD`。
   - 基线：`claude/determined-pasteur-jxpzw8`，或它合并后的 `main`。
   - 依赖的前一个任务还没合并时，从前一个任务的分支新建（叠加），并在报告里写明叠在哪个分支上。
3. 每个任务开工前读：`AGENTS.md`、`docs/SYSTEM_SPEC.md` 中相关小节、任务书开头列出的设计文档，以及 `RB_COMMON.md`（工程约定对所有任务都适用）。
4. 每个任务交付时：
   - `npm test` 和现有浏览器 smoke 全部通过；
   - 按任务书写好验收证据；
   - 同一提交里更新 SYSTEM_SPEC、DESKTOP_IMPLEMENTATION（顶部日期小节）、ROADMAP；
   - 界面相关的任务要附截图（浅色 / 深色、中文 / 英文），并按 `FEATURE_FLAGS.md` 打开对应功能开关。
5. 不开 PR、不合并；报告写明远端分支名和 SHA，推送失败不算交付。secret、本地状态、日志、构建产物不进 Git。
6. 遇到任务书没有覆盖、但会改变用户可见行为的问题：
   - 小而明显的，Astra 按已批准的设计自行决定，报告里写明；
