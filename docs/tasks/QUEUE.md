## 通用做法

1. **交付节奏**（2026-10-03 起）：每完成一个任务就推送并报告，停下等 Claude 审阅后再开始下一个。提示词明确说"不必等审阅"的小项除外。
   - 批内遇到问题，Astra 自己判断：根因清楚、有回归测试的就直接修，修完继续，最后在报告里说明（2026-09-27 用户修订）。
   - 只有涉及产品取舍、或无法确定根因时才停下。
2. **一个任务一个分支**：`codex/tNN-<主题>-YYYYMMDD`。
   - 基线：`claude/determined-pasteur-jxpzw8`，或它合并后的 `main`。
   - 依赖的前一个任务还没合并时，从前一个任务的分支新建（叠加），并在报告里写明叠在哪个分支上。
3. 每个任务开工前读：`AGENTS.md`、`docs/SYSTEM_SPEC.md` 中相关小节、任务书开头列出的设计文档，以及 `RB_COMMON.md`（工程约定对所有任务都适用）。
4. 每个任务交付时：
   - `npm test` 和现有浏览器 smoke 全部通过；
   - 按任务书写好验收证据；
   - 同一提交里更新 SYSTEM_SPEC、DESKTOP_IMPLEMENTATION（顶部日期小节）、ROADMAP；
   - 界面相关的任务要附截图（浅色 / 深色、中文 / 英文），并按 `FEATURE_FLAGS.md` 打开对应功能开关。
5. 不开 PR、不合并；报告写明远端分支名和 SHA，推送失败不算交付。secret、本地状态、日志、构建产物不进 Git。
6. 遇到任务书没有覆盖、但会改变用户可见行为的问题：
   - 小而明显的，Astra 按已批准的设计自行决定，报告里写明；
   - 涉及产品方向的，停下列出选项，由用户决定。
7. **子代理**（用户 2026-10-03 更新）：调用子代理时用 GPT-6.1 Sol（"6.1sol"，与 6 Sol 同价，水平接近 Astra），思考程度用 high；Git 提交与推送用 GPT-6 Luna（"6luna"）。不要使用 GPT-5.6 系列。
   - 由子代理报告结果，执行者复核关键失败，不必亲自逐项执行。
   - 子代理的报告不等于验收：失败项和最终结论由执行者确认，最终由 Claude 审阅。
8. **付费评测的 key**（用户 2026-09-27 更新）：用户授权当前工作区的 OpenCode Go key 在 alpha 发布前持续用于测试。
   - **鼓励多用**（用户 2026-10-03）：额度充足，上月只用了不到 10%。凡是真实模型能提供本地模拟模型给不了的证据（端到端质量、工具选择、提示词效果、回归对比），都应该跑真实评测，不必为省额度而跳过。仍以便宜模型为主，报告里如实写明请求次数与用量。
   - **质量对比要多跑几轮**（2026-10-03 复盘）：便宜模型单次运行波动大，52 题单跑一次的差异（43 / 42 / 39）分不清是改动的效果还是随机波动。改动前后的质量对比，每边至少跑 3 轮，报告每轮结果、平均值和按失败原因的分类；评测基础设施的失败（代理、网络）单独统计，不计入模型质量。
   - 写入 Git 忽略的 `.sciencescope-local/secret/opencode.key` 使用，不提交、不打印、不写进日志和报告；
   - 当前工作区凭据在批次结束及暂停时保留，直到用户要求删除或 alpha 发布前重新确认；不得持久化到用户/系统环境变量。这取代此前“本批结束后删除”的要求。
